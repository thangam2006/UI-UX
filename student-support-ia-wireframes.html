Student Support Service

A mobile-first flow that helps a student understand assigned work, find the required source material, submit proof, and recover cleanly when a reviewer sends work back.

Asha, 19 — Android, intermittent mobile data, first internship. Needs plain instructions and visible progress.
Ravi, 22 — screen magnifier, keyboard user on laptop. Needs scalable text and predictable focus order.
Meera, 20 — shared family device, limited uninterrupted time. Needs saved progress and safe session controls.

04

Desktop adaptation

Assignment detail, adapted. The bottom tab bar becomes a persistent left sidebar, and the single decision moves from two stacked buttons to a side-by-side pair next to the content it affects — better suited to a keyboard-and-mouse session like Ravi's.

NavigationWhat was a 3-item bottom tab bar becomes a persistent left sidebar with full labels — more targets fit, and it stays reachable by keyboard tab order without scrolling past content first.
Content hierarchyThe single mobile column splits into content (left/center) and a status-at-a-glance right rail, so the progress indicator that was buried on mobile is always visible on desktop.
InteractionThe two decision actions sit side by side instead of stacked, matching a mouse/keyboard reading pattern left-to-right rather than a thumb's top-to-bottom reach.
AccessibilitySidebar items and both decision buttons follow a single top-to-bottom, left-to-right focus order; the primary action keeps a 3:1 contrast focus ring against the white content area.
05

Annotations

Navigation model, content hierarchy, and interaction behavior, tied back to the three personas.

Navigation

  • Mobile: fixed bottom tab bar, 3 items max, so it stays usable one-handed on Asha's phone.
  • Desktop: the same 3 destinations move to a left sidebar with visible labels, no icon-only guessing.
  • Every secondary screen (materials, feedback) has one back path and one forward action — never both a back button and a cancel button competing for attention.

Content hierarchy

  • Status (due soon, in review, changes requested) is always the first thing colored on a card — students scan for that before the title.
  • Instructions are shown before required material, and material before the submit action, matching the order a student actually needs it in.
  • Reviewer feedback is split into short, checkable items rather than a paragraph, so Ravi's screen magnifier isn't panning across long lines.

Interaction & states

  • Forms autosave locally; Meera can close the app mid-task on a shared device and pick back up without losing work.
  • The submit button disables with an explanation (never silently) when offline, and re-enables automatically on reconnect — no manual "check connection" step.
  • Focus order follows visual order top-to-bottom on every screen; the primary action always keeps a visible focus ring at 3:1 contrast against its background for keyboard users.

Short explanation

The flow is built around one decision (has the student reviewed enough to submit?) and one recovery loop (reviewer feedback sends them back to the same submit screen with their draft intact). Depth stays shallow on purpose — everything is reachable in three taps from Home — because the three personas share one constraint even though their devices differ: none of them can afford to hunt for where something lives. Mobile is the base layout; the desktop pass only changes how navigation and status are exposed, not the underlying task order, so the same mental model holds on either device.
